# Production rollout policy

Use `scripts/deploy_dokploy.py` for a Kurbis production release. It accepts only a clean checkout exactly matching `origin/main`, runs the rollout behavior suite and the database-backed `first_join_flow` regression before changing Dokploy or respond5, then deploys an immutable `kurbis-release-<full-sha>` tag. The runner stages and validates the complete tracked source manifest on respond5 and rejects untracked or ignored Docker-context inputs; the sole ignored-file exception is the Dokploy `.env`, which Docker context ignore rules must exclude.

The script deliberately keeps Dokploy's production `autoDeploy` setting disabled. That is persistent policy, not a temporary toggle: production changes are initiated only by the verified manual rollout path. The script temporarily selects the immutable release tag, checks the deployment and runtime provenance, then restores the configured source branch (`main`). It restores the previous `BUILD_REVISION` when a rollout is not accepted; on success, it retains the accepted revision pin. The production TLS directory and localhost-only panel bind are maintained in the Dokploy environment.

Respond5 writes the accepted-release marker only after the app and waiting-Pumpkin OCI labels and embedded revisions match the selected SHA, the waiting container's actual Pumpkin executable matches the independently built host-control image, and the worker binary/environment/lease transaction is verified. Any post-mutation failure attempts to restore both prior worker files, restart the previous service, and verify its executable and renewing lease. An unverified rollback retains its protected transaction record for inspection; do not treat it as a successful release.

The first-join regression requires `TEST_DATABASE_URL` to point to a disposable PostgreSQL database. If it is unset or the test fails, the release stops before production changes.

# Production rollout policy

Use `scripts/deploy_dokploy.py` for a Kurbis production release. It accepts only a clean checkout exactly matching `origin/main`, runs the rollout behavior suite and the database-backed `first_join_flow` regression before changing Dokploy or respond5, then deploys an immutable `kurbis-release-<full-sha>` tag. The runner stages and validates the complete tracked source manifest on respond5 and rejects untracked or ignored Docker-context inputs; the sole ignored-file exception is the Dokploy `.env`, which Docker context ignore rules must exclude.

The script requires Dokploy's `docker-compose` mode and an unset custom `command`; it queries Dokploy's `compose.getDefaultCommand` API and verifies that the generated default is the build-enabled command. Stack mode does not support this repository's build directives, and custom commands must not bypass Dokploy's build behavior. The script deliberately keeps Dokploy's production `autoDeploy` setting disabled. That is persistent policy, not a temporary toggle: production changes are initiated only by the verified manual rollout path. The script temporarily selects the immutable release tag, checks the deployment and runtime provenance, then restores the configured source branch (`main`). It restores the previous `BUILD_REVISION` when a rollout is not accepted; on success, it retains the accepted revision pin. The production TLS directory and localhost-only panel bind are maintained in the Dokploy environment.

Before strict baseline verification, respond5 may migrate the one recognized legacy mutable `melon-pumpkin:host-control` reference (or a prior pinned image) to a SHA-pinned image built from the active app revision. It verifies that Pumpkin, the Kurbis WASM plugin, and hosted entrypoint payloads are byte-identical, updates only the protected worker environment, restarts the worker, and verifies the same worker executable and a renewing lease. A mismatch aborts before the app deploy; no server or world data is deleted.

Respond5 writes the accepted-release marker only after app and waiting-Pumpkin OCI labels and embedded revisions match the selected SHA, the waiting container's actual Pumpkin executable matches the independently built host-control image, and the worker binary/environment/lease transaction is verified. If post-deploy worker verification fails or its SSH response is lost, the wrapper idempotently restores the previous worker bundle and asks Dokploy to redeploy the prior app revision. The rollback verifier checks the prior app image's worker executable, SHA-pinned Pumpkin image, service health, and lease before considering recovery verified. An unverified rollback retains protected transaction state; do not treat it as a successful release.

The first-join regression requires `TEST_DATABASE_URL` to point to a disposable PostgreSQL database. If it is unset or the test fails, the release stops before production changes.
